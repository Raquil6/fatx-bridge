# Xbox 360 legacy USB containers

This implementation recognizes the legacy Xbox 360 USB layout in which an
ordinary FAT32 volume contains a hidden `Xbox360` directory with contiguous
files named `Data0000`, `Data0001`, and so on. The first four files are required
by the console format; discovery rejects missing baseline files, gaps, duplicate
numeric indexes, directories, and reparse points. It does not recurse into the
directory and does not alter the FAT32 volume or any container file.

The implementation is intentionally bounded: at most 4096 segment files and at
most 64 GiB in aggregate are accepted. Each segment is opened with read access
and `FileShare.ReadWrite | FileShare.Delete`. `SegmentedReadOnlyStream` owns and
disposes those streams by default; callers that construct it with `leaveOpen:
true` retain ownership. `Xbox360UsbContainerSource.Dispose` closes the wrapper
and therefore all streams opened by its `Open` method.

## Configuration bytes

The first `0x400` bytes of the logical `Data0000` stream are read at most once
for configuration inspection. The field offsets are from the Free60 FATX
reference:

| Offset | Length | Field |
| ---: | ---: | --- |
| `0x228` | `0x14` | device ID |
| `0x23C` | 4 | certificate size (`0x228` or `0x100`) |
| `0x240` | 8 | declared device capacity in bytes |
| `0x248` | 2 | read speed in KB/s |
| `0x24A` | 2 | write speed in KB/s |

FATX multi-byte fields are big-endian. This follows Free60's statement that
FATX values are big-endian and the well-maintained [Velocity `BaseIO` default
and USB configuration parser](https://github.com/hetelek/Velocity/blob/master/XboxInternals/IO/BaseIO.cpp),
which reads these fields without switching away from its big-endian default.
The device ID is never returned or logged as raw bytes; the model exposes only
its SHA-256 fingerprint. The certificate/signature is classified structurally,
but no RSA/SHA-1 verification is attempted. A truncated or unknown
configuration is marked accordingly and still permits a clearly best-effort
read-only layout probe.

## FATX layout probe

The logical stream is probed directly with `FatxVolume.Open`, followed by root
directory validation. Only candidates that pass both checks are returned, and
all candidates are marked read-only. The fixed offsets come from Free60's
[USB Drive table](https://free60.org/System-Software/Systems/FATX/#usb-drive)
and the corresponding [Velocity USB constants](https://raw.githubusercontent.com/hetelek/Velocity/master/XboxInternals/Fatx/FatxConstants.h):

| Candidate | Offset | Fixed length |
| --- | ---: | ---: |
| System Cache | `0x08000400` | `0x047FF000` |
| SysExt / System Auxiliary | `0x08115200` | `0x08000000` |
| SysExt2 / System Extended | `0x12000400` | `0x0DFFFC00` |
| Data | `0x20000000` | logical end of stream |

Free60's rendered table lists the System Cache row's second value as
`0x12000400`; the open-source Velocity implementation supplies the fixed
`UsbSizes::SystemCache = 0x047FF000` used here, while agreeing on the USB
partition offsets and the other fixed sizes. A candidate is never accepted
solely from an offset: its FATX signature, geometry, allocation marker, and
root directory must all validate within the bounded aggregate stream.

The stream may be inspected when the signed configuration is invalid or
unavailable, but this is not a signature recovery path and never enables writes.
There is no mounting, writing, security-sector handling, container creation,
repair, import, resizing, or physical-device formatting in this layer.
